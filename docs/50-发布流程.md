## 版本管理

### 版本号格式

OpenCode 使用语义化版本控制（Semantic Versioning 2.0.0）：

```
MAJOR.MINOR.PATCH
```

- **MAJOR**：不兼容的 API 变更
- **MINOR**：向后兼容的新功能
- **PATCH**：向后兼容的 bug 修复

### 当前版本管理

- **主分支**：`dev`（默认分支）
- **版本存储**：每个包的 `package.json`
- **自动发布**：推送到 `dev` 分支会触发发布工作流

### 版本提升策略

#### 自动版本提升

通过 GitHub Actions 工作流自动处理（`.github/workflows/publish.yml`）：

```yaml
on:
  push:
    branches:
      - dev
  workflow_dispatch:
    inputs:
      bump:
        type: choice
        options:
          - major
          - minor
          - patch
```

#### 手动触发

可以通过 GitHub Actions 手动触发发布：

1. 进入 `.github/workflows/publish.yml`
2. 点击 "Run workflow"
3. 选择分支（`dev`）
4. 选择版本提升类型：
   - `major` - 主版本
   - `minor` - 次版本
   - `patch` - 补丁版本
5. 或输入自定义版本号

#### 版本确定脚本

发布流程使用 `./script/publish-start.ts` 脚本确定版本号：

- 分析自上次发布以来的提交
- 根据提交类型（`feat:`、`fix:`、`BREAKING CHANGE`）自动确定版本提升
- 允许手动覆盖版本号

### 版本示例

```
1.2.0  -> 1.2.1  (patch: bug fix)
1.2.0  -> 1.3.0  (minor: new feature)
1.2.0  -> 2.0.0  (major: breaking change)
```

## 变更日志

### 变更日志管理

OpenCode 目前使用约定式提交消息作为变更日志的主要来源：

- 每个提交的 `feat:` 前缀表示新功能
- 每个提交的 `fix:` 前缀表示 bug 修复
- `BREAKING CHANGE:` 脚注表示破坏性变更

### 自动生成

发布工作流会：

1. 获取自上次发布标签以来的所有提交
2. 根据提交类型和作用域分类
3. 生成 GitHub Release 说明
4. 标记 Pull Request 和贡献者

### 变更日志结构

自动生成的 GitHub Release 说明包含：

```markdown
## What's Changed

### Features

- feat: add dark mode support by @user1
- feat(desktop): add keyboard shortcuts by @user2

### Bug Fixes

- fix(app): resolve crash on startup by @user3
- fix(opencode): memory leak in session cleanup by @user4

### Documentation

- docs: update contributing guidelines by @user5

### Chores

- chore: bump dependency versions by @user6

**Full Changelog**: https://github.com/anomalyco/opencode/compare/v1.2.0...v1.3.0
```

### 手动添加重要说明

在 Release 中可以添加重要说明：

- **升级注意事项**：需要用户采取的步骤
- **已知问题**：已知的限制或问题
- **迁移指南**：如何从旧版本迁移
- **亮点**：重要功能的突出显示

## 发布类型

### 补丁发布（Patch Release）

**触发条件**：

- 仅包含 bug 修复
- 没有新功能
- 没有破坏性变更

**版本示例**：`1.2.0` -> `1.2.1`

**流程**：

1. 修复 bug 并合并到 `dev`
2. 触发 `patch` 版本提升
3. 验证发布
4. 通知用户

**时间表**：可以频繁发布（每周多次）

### 次版本发布（Minor Release）

**触发条件**：

- 包含新功能
- 向后兼容
- 没有破坏性变更

**版本示例**：`1.2.0` -> `1.3.0`

**流程**：

1. 开发新功能并合并到 `dev`
2. 完成功能测试
3. 触发 `minor` 版本提升
4. 完整测试
5. 更新文档
6. 发布公告

**时间表**：每 1-2 周一次

### 主版本发布（Major Release）

**触发条件**：

- 包含破坏性变更
- 重大架构重构
- 不兼容的 API 变更

**版本示例**：`1.2.0` -> `2.0.0`

**流程**：

1. 完成重大开发
2. 编写迁移指南
3. 更新文档
4. 内部测试
5. Beta 测试（可选）
6. 触发 `major` 版本提升
7. 完整验证
8. 发布公告和推广

**时间表**：不定期，可能每月、每季度或每年

## 发布流程

### 1. 准备阶段

#### 确定发布内容

```bash
# 查看自上次发布以来的变更
git log v1.2.0..HEAD --oneline

# 查看 PR 和 Issue
gh pr list --merged --json number,title,author,mergedAt --jq '.[] | select(.mergedAt >= "2025-01-01")'
```

#### 评估版本提升

根据变更内容决定版本提升类型：

- **patch**: 仅 bug 修复
- **minor**: 新功能，向后兼容
- **major**: 破坏性变更

#### 准备发布说明

起草 GitHub Release 说明：

```markdown
## 🎉 v1.3.0

### Highlights

- Feature 1 description
- Feature 2 description

### What's Changed

### Features

...

### Bug Fixes

...

### Upgrade Notes

...
```

### 2. 触发发布

#### 自动触发（推送到 dev）

```bash
git checkout dev
git pull
# 确保所有更改已合并
git push origin dev
```

这将自动触发 `.github/workflows/publish.yml`。

#### 手动触发

1. 进入 GitHub Actions
2. 选择 `publish` workflow
3. 点击 "Run workflow"
4. 选择分支：`dev`
5. 选择版本提升类型：`patch` / `minor` / `major`
6. 或输入自定义版本号

### 3. 发布工作流

`publish.yml` 工作流执行以下步骤：

#### 3.1 发布 CLI 和核心包

```yaml
publish:
  steps:
    - checkout
    - setup bun
    - login to GitHub Container Registry
    - setup QEMU and Buildx (for Docker)
    - setup Node.js
    - setup Git Identity
    - Publish: ./script/publish-start.ts
    - upload artifacts: packages/opencode/dist
```

**脚本行为**：

1. 确定版本号
2. 更新所有包的版本
3. 运行 `bun run build`
4. 发布到 npm
5. 创建 Git 标签
6. 创建 GitHub Release（草稿）
7. 上传 CLI 构建产物

#### 3.2 构建桌面应用

```yaml
publish-tauri:
  strategy:
    matrix:
      settings:
        - host: macos-latest, target: x86_64-apple-darwin
        - host: macos-latest, target: aarch64-apple-darwin
        - host: blacksmith-4vcpu-windows-2025, target: x86_64-pc-windows-msvc
        - host: blacksmith-4vcpu-ubuntu-2404, target: x86_64-unknown-linux-gnu
        - host: blacksmith-4vcpu-ubuntu-2404-arm, target: aarch64-unknown-linux-gnu
```

**每个平台执行**：

1. 签名（macOS）或准备（其他平台）
2. 导入代码签名证书（macOS）
3. 构建桌面应用
4. 签名和公证（macOS）
5. 上传到 GitHub Release

#### 3.3 完成发布

```yaml
publish-release:
  steps:
    - checkout (at release tag)
    - setup bun
    - setup SSH for AUR
    - Complete: ./script/publish-complete.ts
```

**脚本行为**：

1. 发布到 AUR（Arch Linux）
2. 将 GitHub Release 从草稿标记为已发布
3. 触发通知

### 4. 监控发布

监控 GitHub Actions 执行：

```bash
# 查看 workflow 状态
gh run list --workflow=publish.yml

# 查看特定运行
gh run view <run-id>

# 实时日志

```

### 5. 发布后验证

详见 [发布后验证](#发布后验证) 部分。

### 6. 公告

发布完成后，进行公告：

- **博客**（如有）：发布博客文章详细说明新功能

## 回滚策略

### 何时回滚

回滚应在以下情况下考虑：

- **严重 bug**：阻止用户使用核心功能
- **安全漏洞**：发现并已修复的严重安全问题
- **数据丢失**：可能导致用户数据丢失的问题
- **性能崩溃**：导致系统崩溃或严重性能下降
- **依赖问题**：新版本依赖项导致无法解决的问题

### 回滚类型

#### 1. 紧急回滚（Hotfix Patch）

**适用情况**：快速修复小问题

```bash
# 1. 在 dev 分支创建修复分支
git checkout dev
git checkout -b hotfix/urgent-fix

# 2. 修复问题
# ... make changes ...

# 3. 提交和推送
git add .
git commit -m "fix: urgent issue description"
git push origin hotfix/urgent-fix

# 4. 创建 PR 并快速审查
gh pr create --title "fix: urgent issue" --body "Urgent fix for..."

# 5. 合并后立即触发 patch 发布
# (或手动触发 patch 发布)
```

#### 2. 版本回滚

**适用情况**：发布严重问题，需要恢复到上一版本

**步骤**：

1. **停止发布**：如果仍在进行中，取消 GitHub Actions

2. **通知用户**：
   - 在 Discord 发布公告
   - 更新 GitHub Release 说明
   - 在 Twitter/X 发布通知

3. **建议用户降级**：

   ```bash
   # 指定上一版本
   npm i -g opencode-ai@1.2.0

   # 或使用 Homebrew
   brew install opencode@1.2.0
   ```

4. **修复问题**：

   ```bash
   # 基于 dev 创建修复分支
   git checkout dev
   git checkout -b fix/release-issue

   # 修复问题
   # ...

   # 创建 PR
   gh pr create
   ```

5. **发布新版本**：
   - 修复合并后，发布新版本
   - 可以是 `1.3.1`（如果 1.3.0 已发布）或 `1.2.1`（如果 1.3.0 问题严重）

#### 3. 分支回滚（罕见）

**适用情况**：需要完全撤销 dev 分支的更改

```bash
# ⚠️ 谨慎使用，会影响其他开发

# 1. 备份当前状态
git branch backup-dev

# 2. 重置到上一版本标签
git checkout dev
git reset --hard v1.2.0

# 3. 强制推送（需要权限）
git push origin dev --force

# 4. 通知所有开发者
# 通知需要重新基于 dev 分支
```

### 回滚后验证

- [ ] 用户可以降级到上一版本
- [ ] 上一版本工作正常
- [ ] 回滚公告已发布
- [ ] 新的修复 PR 已创建
- [ ] 问题根本原因已识别

### 预防措施

为减少回滚需求：

- **充分的测试**：发布前进行全面测试
- **Beta 测试**：对重大变更进行 Beta 测试
- **渐进式发布**：考虑小范围先发布，观察反馈
- **监控**：密切关注发布后的问题报告
- **快速响应**：准备好快速修复计划

## 常见问题

### Q: 如何决定版本提升类型？

**A**: 根据变更内容：

- `patch`: 仅 bug 修复
- `minor`: 新功能，向后兼容
- `major`: 破坏性变更

发布脚本会自动分析提交消息，但可以手动覆盖。

### Q: 发布需要多长时间？

**A**: 取决于平台：

- CLI 和 npm: ~5-10 分钟
- macOS 构建: ~15-20 分钟（每个架构）
- Windows 构建: ~10-15 分钟
- Linux 构建: ~10-15 分钟（每个架构）

总时间：通常 30-60 分钟。

### Q: 如何修复已发布的版本？

**A**: 使用补丁发布：

1. 在 dev 上修复问题
2. 立即触发 patch 发布
3. 通知用户更新

对于严重问题，可以建议用户降级到上一版本。

### Q: 可以跳过版本号吗？

**A**: 可以通过手动输入自定义版本号：

```yaml
version: "1.4.0" # 跳过 1.3.0
```

但通常不建议，除非有特殊原因。

### Q: 如何创建 Beta 版本？

**A**: 使用 `prerelease` 标签：

```bash
npm version 1.3.0-beta.1
npm publish --tag beta
```

或使用 `snapshot-*` 分支触发预发布：

```bash
git checkout -b snapshot-1.3.0-beta
git push origin snapshot-1.3.0-beta
```

### Q: 发布失败怎么办？

**A**:

1. 查看 GitHub Actions 日志确定失败原因
2. 如果是临时问题，重新触发工作流
3. 如果是代码问题，修复后重新发布
4. 如果是配置问题（证书、令牌），联系维护者

### Q: 如何发布 VSCode 扩展？

**A**: 通过 `.github/workflows/publish-vscode.yml`：

- 自动在发布 opencode 时触发
- 或手动触发
- 发布到 Visual Studio Marketplace

### Q: 如何发布 GitHub Action？

**A**: 通过 `.github/workflows/publish-github-action.yml`：

- 自动在发布 opencode 时触发
- 或手动触发
- 发布到 GitHub Marketplace

### Q: 用户报告新版本问题怎么办？

**A**:

1. 验证问题（尝试重现）
2. 确认是否是回归
3. 如果是严重问题，考虑回滚或紧急修复
4. 创建 issue 跟踪
5. 修复并发布新版本

### Q: 如何监控发布成功率？

**A**: 使用以下方法：

- **npm 下载统计**：`npm view opencode-ai --json`
- **GitHub Release 下载**：查看每个 Release 的下载量
- **错误报告**：监控 Sentry（如果配置）或 GitHub Issues
- **用户反馈**：Discord 和社交媒体

### Q: 可以回滚已合并的 PR 吗？

**A**: 可以，但谨慎使用：

```bash
# 回滚特定 PR
git revert <commit-hash>

# 或回滚到特定提交
git revert --no-commit <commit-range>
git commit
```

然后创建 PR 并发布新版本。
