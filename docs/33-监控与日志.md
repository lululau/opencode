## 概述

OpenCode 实现了全面的日志和监控系统，从应用级别日志到云端遥测数据，提供完整的可观测性。系统支持本地开发调试和生产环境监控，帮助运维团队快速定位和解决问题。

### 监控架构

```
┌─────────────────────────────────────┐
│     应用层日志 (Application)        │
│  - 自定义 Logger                 │
│  - 4 个级别 (DEBUG/INFO/WARN/ERROR) │
│  - 结构化日志 (key=value)          │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│     文件输出 (File Output)          │
│  - ~/.local/share/opencode/log/     │
│  - 自动轮转 (保留 10 个)         │
│  - 时间戳 + 毫秒精度             │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│     云端遥测 (Cloud Telemetry)    │
│  - Honeycomb 指标               │
│  - Cloudflare Logpush             │
│  - API 请求/响应分析              │
└─────────────────────────────────────┘
```

### 核心组件

| 组件               | 实现位置                                             | 功能                               |
| ------------------ | ---------------------------------------------------- | ---------------------------------- |

## 日志级别

### 级别定义

OpenCode 使用四个标准日志级别：

**实现位置**：`packages/opencode/src/util/log.ts`

```typescript
export namespace Log {
  export const Level = z.enum(["DEBUG", "INFO", "WARN", "ERROR"])
  export type Level = z.infer<typeof Level>

  const levelPriority: Record<Level, number> = {
    DEBUG: 0,
    INFO: 1,
    WARN: 2,
    ERROR: 3,
  }
}
```

### 级别说明

| 级别      | 优先级 | 用途                       | 示例场景                       |
| --------- | ------ | -------------------------- | ------------------------------ |
| **DEBUG** | 0      | 详细的调试信息，仅用于开发 | 函数调用细节、内部状态、变量值 |
| **INFO**  | 1      | 一般信息，记录正常操作     | 用户登录、会话创建、请求处理   |
| **WARN**  | 2      | 警告信息，不影响功能       | 配置缺失、重试操作、降级服务   |
| **ERROR** | 3      | 错误信息，需要关注         | 认证失败、API 错误、异常捕获   |

### 级别过滤

```typescript
let level: Level = "INFO"

function shouldLog(input: Level): boolean {
  return levelPriority[input] >= levelPriority[level]
}

// 示例：当前级别 INFO
shouldLog("DEBUG") // false（不输出）
shouldLog("INFO") // true（输出）
shouldLog("WARN") // true（输出）
shouldLog("ERROR") // true（输出）
```

### 默认级别

| 环境         | 默认级别 | 原因             |
| ------------ | -------- | ---------------- |
| **本地开发** | `DEBUG`  | 便于调试和开发   |
| **生产环境** | `INFO`   | 平衡详细度和性能 |
| **容器部署** | `INFO`   | 避免过多日志输出 |
| **测试环境** | `WARN`   | 减少测试日志噪音 |

## 日志输出

### 日志格式

OpenCode 使用结构化日志格式，包含时间戳、时间增量、标签和消息。

**格式**：

```
LEVEL YYYY-MM-DDTHH:MM:SS +Xms key1=value1 key2=value2 message
```

**示例**：

```log
INFO  2025-01-22T14:30:15 +120ms service=session session_id=ses_abc123 user_id=user_456 action=created
WARN  2025-01-22T14:30:20 +5ms  service=mcp server_id=mcp_xyz connection_failed reason=timeout
ERROR 2025-01-22T14:30:25 +892ms service=api error=Connection refused endpoint=/v1/chat
```

### 日志结构

**实现**：`packages/opencode/src/util/log.ts`

```typescript
function build(message: any, extra?: Record<string, any>) {
  // 1. 处理标签
  const prefix = Object.entries({ ...tags, ...extra })
    .filter(([_, value]) => value !== undefined && value !== null)
    .map(([key, value]) => {
      if (value instanceof Error) return `${key}=${formatError(value)}`
      if (typeof value === "object") return `${key}=${JSON.stringify(value)}`
      return `${key}=${value}`
    })
    .join(" ")

  // 2. 时间戳和增量
  const now = new Date()
  const diff = now.getTime() - last
  last = now.getTime()

  // 3. 组合输出
  return [now.toISOString().split(".")[0], `+${diff}ms`, prefix, message].filter(Boolean).join(" ") + "\n"
}
```

### 时间增量跟踪

**特性**：

- 记录自上次日志的毫秒数
- 帮助分析性能瓶颈
- 自动计算，无需手动计时

**示例**：

```log
INFO  2025-01-22T14:30:00 +0ms    service=api request_received id=req_123
INFO  2025-01-22T14:30:00 +5ms   service=api auth_verified user_id=user_456
INFO  2025-01-22T14:30:00 +120ms service=api request_processed id=req_123 duration=125ms
```

分析：

- 请求接收：0ms
- 认证验证：5ms
- 总处理时间：125ms
- 认证耗时：5ms
- 业务逻辑耗时：120ms

function formatError(error: Error, depth = 0): string {
  const result = error.message
  return error.cause instanceof Error && depth < 10

    : result
}

async function cleanup(dir: string) {
  const glob = new Bun.Glob("????-??-??T??????.log")
  const files = await Array.fromAsync(glob.scan({ cwd: dir, absolute: true }))

  // 保留最后 10 个文件
  if (files.length <= 10) return

## 性能监控

### 时间测量

**Logger.time() 方法**：

```typescript
export interface Logger {
  time(
    message: string,
    extra?: Record<string, any>,
  ): {
    stop(): void
    [Symbol.dispose](): void
  }
}
```

**实现**：

```typescript
time(message: string, extra?: Record<string, any>) {
  const now = Date.now()
  result.info(message, { status: "started", ...extra })

  function stop() {
    result.info(message, {
      status: "completed",
      duration: Date.now() - now,
      ...extra,
    })
  }

  return {
    stop,
    [Symbol.dispose]() { stop() },  // 支持 using 语法
  }
}
```

**使用示例**：

```typescript
// 方法 1：手动停止
const timer = log.time("api_request", { endpoint: "/v1/chat" })
// ... 执行请求 ...
timer.stop()

// 方法 2：自动停止（using）
{
  using timer = log.time("database_query", { query: "SELECT * FROM users" })
  const result = await db.query(query)
  // timer 自动停止
}
```

**输出**：

```log
INFO  2025-01-22T14:30:00 +0ms    service=database query=SELECT * FROM users status=started
INFO  2025-01-22T14:30:00 +123ms service=database query=SELECT * FROM users status=completed duration=123ms
```

### 操作耗时分析

**示例：完整请求生命周期**

```typescript
const log = Log.create({ service: "api" })

using authTimer = log.time("auth", { userId: "user_123" })
await authenticate(userId)
// authTimer 自动停止，输出耗时

using dbTimer = log.time("database", { query: "SELECT * FROM users" })

// dbTimer 自动停止，输出耗时

using llmTimer = log.time("llm_call", { model: "claude-sonnet-4" })

// llmTimer 自动停止，输出耗时

log.info("request_completed", { total_duration: auth_duration + db_duration + llm_duration })
```

**日志分析**：

```log
INFO  2025-01-22T14:30:00 +0ms    service=api auth status=started
INFO  2025-01-22T14:30:00 +45ms   service=api auth status=completed duration=45ms
INFO  2025-01-22T14:30:00 +50ms   service=api database status=started
INFO  2025-01-22T14:30:00 +120ms  service=api database status=completed duration=70ms
INFO  2025-01-22T14:30:00 +125ms  service=api llm_call status=started
INFO  2025-01-22T14:30:00 +2345ms service=api llm_call status=completed duration=2220ms
INFO  2025-01-22T14:30:00 +2350ms service=api request_completed total_duration=2335ms
```

分析：

- 认证：45ms（2%）
- 数据库：70ms（3%）
- LLM 调用：2220ms（95%）
- 总计：2335ms

**优化建议**：LLM 调用是主要瓶颈，考虑：

1. 使用更快的模型
2. 并行处理多个请求
3. 缓存常见查询结果

## 遥测数据

### Honeycomb 集成

OpenCode 使用 Honeycomb 进行生产环境遥测。

**实现位置**：`packages/console/function/src/log-processor.ts`

#### 1. Log Processor

```typescript
// Cloudflare Worker 日志处理器
export default {
  async tail(events: TailEvent[]) {
    for (const event of events) {
      const logs = event.logs || []

      for (const log of logs) {
        // 提取指标（_metric: 前缀）
        if (log.message.startsWith("_metric:")) {
          const metric = JSON.parse(log.message.slice(8))

          await fetch("https://api.honeycomb.io/1/events", {
            method: "POST",
            headers: {
              "X-Honeycomb-Team": Resource.HONEYCOMB_TEAM,
              "X-Honeycomb-Dataset": "opencode-api",
              "Content-Type": "application/json",
            },
            body: JSON.stringify({
              time: event.eventTimestampMs,
              ...metric,
            }),
          })
        }
      }
    }
  },
}
```

## 监控最佳实践

### 日志记录原则

#### 1. 结构化日志

**❌ 错误**：

```typescript
console.log("User logged in at " + new Date())
console.error("Failed to connect to database")
```

**✅ 正确**：

```typescript
log.info("user_login", {
  userId: "user_123",
  timestamp: new Date().toISOString(),
  ip_address: request.ip,
})
log.error("database_connection_failed", {
  error: e.message,
  host: db.host,
  port: db.port,
  attempt: 3,
})
```

#### 2. 使用适当的日志级别

| 场景                   | 级别    | 原因                   |
| ---------------------- | ------- | ---------------------- |
| 用户登录               | `INFO`  | 正常操作，需要记录     |
| API 密钥创建           | `INFO`  | 正常操作，需要审计     |
| 配置缺失（使用默认值） | `WARN`  | 不影响功能，但需要注意 |
| 网络超时（自动重试）   | `WARN`  | 不影响功能，但表明问题 |
| 认证失败               | `WARN`  | 预期行为，但频率需监控 |
| 数据库连接失败         | `ERROR` | 功能受影响，需要修复   |
| 未捕获的异常           | `ERROR` | 严重问题，需要立即关注 |

#### 3. 记录足够的上下文

```typescript
// ✅ 好的日志
log.error("api_request_failed", {
  endpoint: "/v1/chat",
  method: "POST",
  user_id: userId,
  session_id: sessionId,
  error: e.message,
  stack: e.stack,
  attempt: 3,
  duration_ms: 5000,
})

// ❌ 不够的日志
log.error("API failed")
```

#### 4. 避免记录敏感数据

```typescript
// ❌ 错误：记录密码
log.info("user_login", {
  username: "alice",
  password: "secret123", // 危险！
})

// ✅ 正确：记录哈希或掩码
log.info("user_login", {
  username: "alice",
  password_hash: sha256("secret123"), // 或
  password_mask: "********",
})
```

### 性能监控原则

#### 1. 记录关键操作的耗时

```typescript
using dbTimer = log.time("database_query", { query: "SELECT * FROM users WHERE id = ?" })
const user = await db.query(query)
// dbTimer 自动停止

using apiTimer = log.time("external_api_call", { endpoint: "https://api.example.com/data" })
const data = await fetch(endpoint)
// apiTimer 自动停止
```

#### 2. 使用时间增量分析

```log
INFO  2025-01-22T14:30:00 +0ms    auth_started
INFO  2025-01-22T14:30:00 +45ms   auth_completed
INFO  2025-01-22T14:30:00 +50ms   db_query_started
INFO  2025-01-22T14:30:00 +120ms  db_query_completed
INFO  2025-01-22T14:30:00 +125ms  llm_call_started
INFO  2025-01-22T14:30:00 +2345ms llm_call_completed
```

分析：

- 认证：45ms
- 数据库：70ms
- LLM 调用：2220ms
- 总计：2335ms

#### 3. 监控资源使用

```bash
# 监控 CPU 使用率
top -b -n 1 | grep "Cpu(s)" | awk '{print $2}'

# 监控内存使用率
free | grep Mem | awk '{print ($3/$2) * 100.0}'

# 监控磁盘 I/O
iostat -x 1

# 监控网络流量
iftop
```

### 遥测原则

#### 1. 不要在生产环境中过度记录

```typescript
// ❌ 错误：开发环境使用 DEBUG
if (production) {
  Log.init({ level: "DEBUG" })
}

// ✅ 正确：生产环境使用 INFO
if (production) {
  Log.init({ level: "INFO" })
}
```

#### 2. 采样高频率事件

```typescript
// 对于高频事件，使用采样
const sampleRate = 0.1 // 10% 采样

function logRequest(request) {
  if (Math.random() < sampleRate) {
    logger.metric({
      endpoint: request.path,
      duration_ms: request.duration,
      status: request.status,
    })
  }
}
```

#### 3. 聚合遥测数据

```honeycomb
# 不要记录每个事件
event: request
duration_ms: 123

# 而是使用聚合
event: request_summary
avg_duration_ms: 125
p95_duration_ms: 234
p99_duration_ms: 456
request_count: 1000
error_rate: 0.02
```

## 故障排查

### 常见问题

#### 问题 1：日志文件过大

**症状**：

- `~/.local/share/opencode/log/` 目录占用大量磁盘空间
- 日志文件增长过快

**原因**：

- 日志级别设置为 DEBUG
- 日志轮转未正常工作
- 应用产生过多日志

**解决方案**：

```bash
# 1. 检查当前日志级别
opencode config show

# 2. 调整为 INFO 或 WARN
export OPENCODE_LOG_LEVEL=INFO

# 3. 手动清理旧日志
find ~/.local/share/opencode/log/ -name "*.log" -mtime +7 -delete

# 4. 设置日志轮转
# 编辑 /etc/logrotate.d/opencode
/var/log/opencode/*.log {
    daily
    rotate 14
    compress
    delaycompress
    notifempty
    create 0640 opencode opencode
}
```

#### 问题 2：缺少错误日志

**症状**：

- 应用崩溃但日志中没有错误信息
- 错误信息在标准输出而非日志文件

**原因**：

- 全局错误处理器未注册
- 错误发生在 logger 初始化之前
- 错误在子进程中

**解决方案**：

```bash
# 1. 检查全局处理器是否正确设置
grep "unhandledRejection" packages/opencode/src/index.ts
grep "uncaughtException" packages/opencode/src/index.ts

# 2. 检查日志初始化顺序
# 确保 Log.init() 在错误处理器之前

# 3. 使用 --print-logs 临时输出到控制台
opencode serve --print-logs

# 4. 检查系统日志
journalctl -u opencode -f  # systemd
dmesg  # 内核日志
```

#### 问题 3：性能问题难以追踪

**症状**：

- 响应慢，但日志中没有明确的耗时信息
- 不知道瓶颈在哪里

**解决方案**：

```bash
# 1. 启用 DEBUG 日志级别
export OPENCODE_LOG_LEVEL=DEBUG

# 2. 使用 log.time() 标记关键操作
const timer = log.time("operation")
// ... 执行 ...
timer.stop()

# 3. 使用性能分析工具
# Bun 内置性能分析
bun --profile opencode

# 或使用火焰图
bun run --trace

# 4. 监控系统资源
htop  # CPU 和内存
iotop  # 磁盘 I/O
iftop  # 网络
```

#### 问题 4：遥测数据不完整

**症状**：

- Honeycomb 中缺少指标
- Logpush 未推送日志

**解决方案**：

```bash
# 1. 检查 Cloudflare Worker 配置
grep "logpush" infra/app.ts

# 2. 验证 Honeycomb API 密钥
export HONEYCOMB_API_KEY=your_key_here

# 3. 检查网络连接
curl https://api.honeycomb.io/1/events \
  -H "X-Honeycomb-Team: your-team" \
  -H "X-Honeycomb-EventTime: $(date +%s)000" \
  -d '{"test": true}'

# 4. 查看 Cloudflare Worker 日志
wrangler tail opencode-api
```

### 调试技巧

#### 1. 临时启用详细日志

```bash
# 当前会话
export OPENCODE_LOG_LEVEL=DEBUG
opencode serve

# 单次命令
OPENCODE_LOG_LEVEL=DEBUG opencode run --message "test"

# 使用 --print-logs 实时查看
opencode serve --print-logs --log-level DEBUG
```

#### 2. 过滤特定服务

```bash
# 只看 API 日志
grep "service=api" ~/.local/share/opencode/log/*.log

# 只看错误
grep "ERROR" ~/.local/share/opencode/log/*.log

# 组合过滤
grep "ERROR.*service=mcp" ~/.local/share/opencode/log/*.log
```

#### 3. 时间范围查询

```bash
# 查看今天的日志
grep "2025-01-22" ~/.local/share/opencode/log/*.log

# 查看特定小时
grep "2025-01-22T14:" ~/.local/share/opencode/log/*.log

# 使用 ripgrep 查询
rg "2025-01-22T1[4-9]:" ~/.local/share/opencode/log/  # 下午 2-10 点
```

#### 4. 实时监控

```bash
# 使用 tail 实时查看
tail -f ~/.local/share/opencode/log/dev.log

# 过滤实时输出
tail -f ~/.local/share/opencode/log/dev.log | grep ERROR

# 使用 less 查看
less +F ~/.local/share/opencode/log/dev.log  # F=实时模式
```
