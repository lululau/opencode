## 概述

技能（Skills）是 OpenCode 中的一种轻量级扩展机制，通过 Markdown 文件定义专业化的知识和逐步指导。技能允许 AI 代理访问详细的任务指南，从而更准确、更高效地完成特定类型的工作。

### 技能 vs 插件

| 特性           | 技能 (Skills)      | 插件 (Plugins)        |
| -------------- | ------------------ | --------------------- |
| **格式**       | Markdown + YAML    | TypeScript/JavaScript |
| **编程**       | 无需编程           | 需要编程              |
| **复杂度**     | 简单               | 复杂                  |
| **API 访问**   | 仅限内容           | 完整 API 访问         |
| **自定义工具** | 不支持             | 支持                  |
| **适用场景**   | 任务指导、最佳实践 | 外部集成、复杂逻辑    |

### 核心特性

- **简单**: 只需创建 Markdown 文件
- **版本控制友好**: 文本文件，易于 diff 和 merge
- **自动发现**: 自动从目录扫描技能文件
- **权限控制**: 支持代理级别的权限过滤
- **格式化输出**: 自动格式化技能内容展示
- **兼容 Claude Code**: 支持 `.claude/skills/` 目录

## 技能定义与结构

### 文件位置

技能文件位于以下目录：

```
.opencode/skill/**/SKILL.md    # OpenCode 技能
.claude/skills/**/SKILL.md    # Claude Code 技能（兼容）
~/.claude/skills/**/SKILL.md   # 全局 Claude 技能
```

### 文件命名

- **推荐**: `SKILL.md`（大写）
- **文件位置**: 技能目录下的任意子目录
- **目录名**: 不会被使用，仅用于组织

```
.opencode/skill/
├── git/            # Git 相关技能
│   ├── SKILL.md    # Git 主技能
│   └── advanced/   # 高级 Git 技能
│       └── SKILL.md
├── testing/        # 测试相关技能
│   └── SKILL.md
└── documentation/  # 文档相关技能
    └── SKILL.md
```

### 文件结构

技能文件使用 **Markdown + YAML frontmatter** 格式。

**代码位置**: `/packages/opencode/src/config/markdown.ts:68-84`

```markdown
---
name: skill-name
description: Brief description of what this skill does
---

# Detailed skill content

Here you provide step-by-step instructions, guidelines, and
examples for the AI agent to follow.

## Step 1: Do this

Explanation...

## Step 2: Then do that

Explanation...

## Examples

Example code or usage patterns...
```

### YAML Frontmatter 解析

**代码位置**: `/packages/opencode/src/config/markdown.ts:5-66`

Frontmatter 必须包含特定字段：

```yaml
---
name: required-skill-name
description: Required skill description
# 可选字段（如果存在）
optionalField: value
otherField: another value
---
# Markdown content starts here
```

**Frontmatter 预处理**:

OpenCode 会自动处理 frontmatter 中的某些格式问题：

1. **跳过注释行**: 以 `#` 开头的行
2. **跳过空行**
3. **处理缩进延续**: 支持多行值
4. **自动转换包含冒号的值**: 使用块标量（`|`）而非行内标量

**示例**:

```yaml
---
# 这是一个注释
name: git-flow

# 如果值包含冒号，自动使用块标量
description: |
  Git flow workflow for branch management
  Supports feature, release, and hotfix branches

# 多行值
workflow: |
  1. Create feature branch
  2. Develop and commit
  3. Create pull request
  4. Code review
  5. Merge to main
---
Content...
```

## 技能参数

### 必需参数

#### name

技能的唯一标识符，用于引用技能。

```yaml
---
name: git-rebase
---
```

**规则**:

- 必须唯一
- 使用 kebab-case（小写、连字符）
- 避免特殊字符
- 描述性强

**好的示例**:

```yaml
---
name: docker-container-debugging
name: react-component-testing
name: api-rate-limiting
```

**避免的示例**:

```yaml
---
name: git
name: debug
name: 123-skills
```

#### description

简短描述技能的功能，用于 AI 选择技能。

```yaml
---
description: Advanced Git rebase workflow for interactive branch management
---
```

**规则**:

- 1-2 句话
- 明确技能用途
- 提及关键功能

**好的示例**:

```yaml
---
description: Database migration strategies and best practices for PostgreSQL
description: React component testing with Jest and React Testing Library
description: Kubernetes deployment patterns and troubleshooting
```

### 可选参数

额外的 frontmatter 字段会被忽略，但可以用于文档目的。

```yaml
---
name: my-skill
description: Skill description
author: Your Name
version: 1.0.0
tags: [category1, category2]
related: [other-skill]
---
Content...
```

### 详细阶段

#### 1. 发现阶段

**代码位置**: `/packages/opencode/src/skill/skill.ts:44-126`

```typescript
export const state = Instance.state(async () => {
  const skills: Record<string, Info> = {}

  // 添加技能函数
  const addSkill = async (match: string) => {
    const md = await ConfigMarkdown.parse(match).catch((err) => {
      // 处理解析错误
      const message = ConfigMarkdown.FrontmatterError.isInstance(err)
        ? err.data.message
        : `Failed to parse skill ${match}`
      Bus.publish(Session.Event.Error, {
        error: new NamedError.Unknown({ message }).toObject(),
      })
      log.error("failed to load skill", { skill: match, err })
      return undefined
    })

    if (!md) return

    // 解析必需字段
    const parsed = Info.pick({ name: true, description: true }).safeParse(md.data)
    if (!parsed.success) return

    // 警告重复技能名称
    if (skills[parsed.data.name]) {
      log.warn("duplicate skill name", {
        name: parsed.data.name,
        existing: skills[parsed.data.name].location,
        duplicate: match,
      })
    }

    // 注册技能
    skills[parsed.data.name] = {
      name: parsed.data.name,
      description: parsed.data.description,
      location: match,
    }
  }

  // 扫描 .claude/skills/ 目录
  if (!Flag.OPENCODE_DISABLE_CLAUDE_CODE_SKILLS) {
    for (const dir of claudeDirs) {
      const matches = await Array.fromAsync(
        CLAUDE_SKILL_GLOB.scan({
          cwd: dir,
          absolute: true,
          onlyFiles: true,
          followSymlinks: true,
          dot: true,
        }),
      )
      for (const match of matches) {
        await addSkill(match)
      }
    }
  }

  // 扫描 .opencode/skill/ 目录
  for (const dir of await Config.directories()) {
    for await (const match of OPENCODE_SKILL_GLOB.scan({
      cwd: dir,
      absolute: true,
      onlyFiles: true,
      followSymlinks: true,
    })) {
      await addSkill(match)
    }
  }

  return skills
})
```

export const SkillTool = Tool.define("skill", async (ctx) => {
  const skills = await Skill.all()

  // 权限过滤
  const agent = ctx?.agent
  const accessibleSkills = agent
    ? skills.filter((skill) => {
        const rule = PermissionNext.evaluate("skill", skill.name, agent.permission)
        return rule.action !== "deny"
      })
    : skills

  // 生成动态描述
  const description = /* ... */

  // 定义参数
  const parameters = z.object({
    name: z.string().describe(`The skill identifier from available_skills${hint}`)
  })

  return {
    description,
    parameters,
    async execute(params: z.infer<typeof parameters>, ctx) {
      // 获取技能
      const skill = await Skill.get(params.name)

      if (!skill) {
        const available = await Skill.all().then((x) => Object.keys(x).join(", "))
        throw new Error(`Skill "${params.name}" not found. Available skills: ${available || "none"}`)
      }

      // 权限请求
      await ctx.ask({
        permission: "skill",
        patterns: [params.name],
        always: [params.name],
        metadata: {},
      })

      // 解析技能内容
      const parsed = await ConfigMarkdown.parse(skill.location)
      const dir = path.dirname(skill.location)

      // 格式化输出
      const output = [
        `## Skill: ${skill.name}`,
        "",
        `**Base directory**: ${dir}`,
        "",
        parsed.content.trim()
      ].join("\n")

      return {
        title: `Loaded skill: ${skill.name}`,
        output,
        metadata: {
          name: skill.name,
          dir,
        },
      }
    },
  }
})

### ConfigMarkdown 解析

**代码位置**: `/packages/opencode/src/config/markdown.ts:68-84`

```typescript
export async function parse(filePath: string) {
  const raw = await Bun.file(filePath).text()
  const template = preprocessFrontmatter(raw)

  try {
    const md = matter(template)
    return md
  } catch (err) {
    throw new FrontmatterError(
      {
        path: filePath,
        message: `${filePath}: Failed to parse YAML frontmatter: ${err instanceof Error ? err.message : String(err)}`,
      },
      { cause: err },
    )
  }
}
```

**Frontmatter 预处理**:

```typescript
export function preprocessFrontmatter(content: string): string {
  const match = content.match(/^---\r?\n([\s\S]*?)\r?\n---/)
  if (!match) return content

  const frontmatter = match[1]
  const lines = frontmatter.split("\n")
  const result: string[] = []

  for (const line of lines) {
    // 跳过注释和空行
    if (line.trim().startsWith("#") || line.trim() === "") {
      result.push(line)
      continue
    }

    // 跳过续行（缩进）
    if (line.match(/^\s+/)) {
      result.push(line)
      continue
    }

    // 匹配 key: value 模式
    const kvMatch = line.match(/^([a-zA-Z_][a-zA-Z0-9_]*)\s*:\s*(.*)$/)
    if (!kvMatch) {
      result.push(line)
      continue
    }

    const key = kvMatch[1]
    const value = kvMatch[2].trim()

    // 如果值为空、已引用或使用块标量，跳过
    if (value === "" || value === ">" || value === "|" || value.startsWith('"') || value.startsWith("'")) {
      result.push(line)
      continue
    }

    // 如果值包含冒号，转换为块标量
    if (value.includes(":")) {
      result.push(`${key}: |`)
      result.push(`  ${value}`)
      continue
    }

    result.push(line)
  }

  const processed = result.join("\n")
  return content.replace(frontmatter, () => processed)
}
```

## 完整示例

### 示例 1: Git 工作流技能

**文件**: `.opencode/skill/git/flow/SKILL.md`

````markdown
---
name: git-flow
description: Git flow workflow for branch management with feature, release, and hotfix branches
---

# Git Flow Workflow

You are an expert in Git flow branch management. Follow this workflow when the user needs to manage branches, releases, or hotfixes.

## Core Concepts

- **main**: Production-ready code
- **develop**: Development branch where features are merged
- **feature/<name>**: Feature branches off develop
- **release/<version>**: Release preparation branches off develop
- **hotfix/<version>**: Hotfix branches off main

## Feature Branch Workflow

When creating a new feature:

1. **Create feature branch**
   ```bash
   git checkout develop
   git pull
   git checkout -b feature/feature-name
   ```
````

2. **Develop the feature**
   - Make commits regularly
   - Write descriptive commit messages
   - Keep changes focused

3. **Finish the feature**

   ```bash
   git checkout develop
   git merge --no-ff feature/feature-name
   git branch -d feature/feature-name
   ```

4. **Push changes**
   ```bash
   git push origin develop
   ```

## Release Branch Workflow

When preparing a release:

1. **Create release branch**

   ```bash
   git checkout develop
   git pull
   git checkout -b release/1.0.0
   ```

2. **Prepare release**
   - Update version numbers
   - Update CHANGELOG.md
   - Fix release-specific bugs

3. **Merge release**

   ```bash
   # Merge to main and tag
   git checkout main
   git merge --no-ff release/1.0.0
   git tag -a v1.0.0 -m "Release version 1.0.0"

   # Merge back to develop
   git checkout develop
   git merge --no-ff release/1.0.0

   # Remove release branch
   git branch -d release/1.0.0
   ```

## Hotfix Branch Workflow

When fixing a critical production bug:

1. **Create hotfix branch**

   ```bash
   git checkout main
   git pull
   git checkout -b hotfix/1.0.1
   ```

2. **Fix the bug**
   - Make minimal changes
   - Test thoroughly
   - Update version numbers

3. **Merge hotfix**

   ```bash
   # Merge to main and tag
   git checkout main
   git merge --no-ff hotfix/1.0.1
   git tag -a v1.0.1 -m "Hotfix version 1.0.1"

   # Merge back to develop
   git checkout develop
   git merge --no-ff hotfix/1.0.1

   # Remove hotfix branch
   git branch -d hotfix/1.0.1
   ```

## Important Notes

- Always fetch and pull before creating branches
- Use `--no-ff` to preserve merge history
- Delete branches after merging
- Tag all releases
- Test hotfixes thoroughly before merging to main

````

### 示例 2: React 组件测试技能

```markdown
---
name: react-component-testing
description: Comprehensive React component testing with Jest and React Testing Library

# React Component Testing

You are an expert in testing React components using Jest and React Testing Library. Follow these guidelines when writing or reviewing tests.

## Testing Philosophy

1. **Test behavior, not implementation**: Focus on what the component does, not how it does it
2. **User-centric**: Test from the user's perspective
3. **Avoid testing implementation details**: Don't test internal state or component structure
4. **Keep it simple**: Write simple, readable tests

## Setup

Ensure the following imports are available:

```typescript
import { render, screen, fireEvent, waitFor } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
````

## Test Structure

### Basic Component Test

```typescript
describe('MyComponent', () => {
  it('renders correctly', () => {
    render(<MyComponent />)
    expect(screen.getByText('Hello')).toBeInTheDocument()
  })
})
```

### Testing User Interactions

```typescript
describe('Button Component', () => {
  it('calls onClick when clicked', async () => {
    const handleClick = vi.fn()
    render(<Button onClick={handleClick}>Click me</Button>)

    const button = screen.getByRole('button', { name: 'Click me' })
    await userEvent.click(button)

    expect(handleClick).toHaveBeenCalledTimes(1)
  })
})
```

### Testing Async Behavior

```typescript
describe('AsyncComponent', () => {
  it('displays loading state initially', () => {
    render(<AsyncComponent fetchData={fetchData} />)
    expect(screen.getByText('Loading...')).toBeInTheDocument()
  })

  it('displays data after fetch', async () => {
    const mockData = { name: 'Test' }
    vi.spyOn(fetchData, 'fetch').mockResolvedValue(mockData)

    render(<AsyncComponent fetchData={fetchData} />)

    await waitFor(() => {
      expect(screen.getByText('Test')).toBeInTheDocument()
    })
  })
})
```

## Best Practices

### DO ✅

- Use semantic queries (`getByRole`, `getByLabelText`)
- Test user interactions with `userEvent`
- Wait for async operations with `waitFor`
- Test accessible queries
- Mock external dependencies
- Test error states and edge cases

### DON'T ❌

- Don't test internal state directly
- Don't test implementation details (class names, etc.)
- Don't use `innerHTML` for assertions
- Don't over-mock
- Don't test library components
- Don't write brittle tests that break on UI changes

## Query Priorities

When selecting elements, prefer in order:

1. `getByRole('button', { name: 'Submit' })` - Most accessible
2. `getByLabelText('Username')` - Form elements
3. `getByPlaceholderText('Search...')` - Input fields
4. `getByText('Hello World')` - Text content
5. `getByTestId('submit-button')` - Last resort

## Common Test Scenarios

### Form Submission

```typescript
it('submits form with valid data', async () => {
  const handleSubmit = vi.fn()
  render(<LoginForm onSubmit={handleSubmit} />)

  await userEvent.type(screen.getByLabelText('Username'), 'testuser')
  await userEvent.type(screen.getByLabelText('Password'), 'password123')
  await userEvent.click(screen.getByRole('button', { name: 'Login' }))

  await waitFor(() => {
    expect(handleSubmit).toHaveBeenCalledWith({
      username: 'testuser',
      password: 'password123'
    })
  })
})
```

### Conditional Rendering

```typescript
it('shows error message when form is invalid', () => {
  render(<Form initialData={{ email: 'invalid' }} />)

  expect(screen.getByText('Invalid email')).toBeInTheDocument()
})

it('hides error message when form is valid', () => {
  render(<Form initialData={{ email: 'valid@example.com' }} />)

  expect(screen.queryByText('Invalid email')).not.toBeInTheDocument()
})
```

## Debugging Failed Tests

If a test fails:

1. **Use debug()**: Add `screen.debug()` to see the rendered output
2. **Check for timing issues**: Add `waitFor` if elements appear asynchronously
3. **Verify queries**: Ensure query selectors are correct
4. **Check for multiple matches**: Use `getAllByRole` if multiple elements match
5. **Review test isolation**: Ensure tests don't depend on each other

### 示例 3: API 设计技能

**文件**: `.opencode/skill/api-design/SKILL.md`

```markdown
---
name: api-design
description: RESTful API design principles and best practices with OpenAPI specification
---

# RESTful API Design

You are an expert API architect. Follow these principles when designing or reviewing RESTful APIs.

## Core Principles

1. **Resource-based**: APIs should be resource-oriented
2. **Stateless**: Each request contains all necessary information
3. **Uniform interface**: Consistent conventions
4. **Layered system**: Client shouldn't know about servers, databases, etc.
5. **Cacheable**: Responses should indicate cacheability

## URL Design

### Resource Naming

- Use **nouns**, not verbs
- Use **plural** for collections
- Use **kebab-case** for multi-word resources

````

GET /users ✅ Good
GET /getUser ❌ Bad (verb)
GET /user ❌ Bad (singular)

GET /user-preferences ✅ Good
GET /userPreferences ❌ Bad (camelCase)

```

### Resource Hierarchy

```

GET /users # List users
GET /users/123 # Get specific user
GET /users/123/posts # Get user's posts
GET /users/123/posts/456 # Get specific post

```

### Query Parameters

- Use query strings for filtering, sorting, pagination
- Use consistent parameter names

```

GET /users?page=2&limit=25
GET /users?sort=name:asc
GET /users?status=active&role=admin

````

## HTTP Methods

### GET

- Retrieve resources
- Should be **idempotent** (same result on repeated calls)
- Should be **safe** (no side effects)

```typescript
// List users
GET /users

// Get user
GET /users/123
````

### POST

- Create new resources
- Not idempotent (each call creates a new resource)
- Return `201 Created` with `Location` header

```typescript
// Create user
POST /users
Content-Type: application/json

{
  "name": "John Doe",
  "email": "john@example.com"
}

Response: 201 Created
Location: /users/123
```

### PUT

- Update entire resource
- **Idempotent**
- Replace all fields

```typescript
// Update user (all fields)
PUT /users/123
Content-Type: application/json

{
  "name": "Jane Doe",
  "email": "jane@example.com"
}
```

### PATCH

- Partial update
- **Idempotent** (if patches are cumulative)
- Update only provided fields

```typescript
// Update user (partial)
PATCH /users/123
Content-Type: application/json

{
  "name": "Jane Doe"
}
```

### DELETE

- Delete resource
- **Idempotent**

```typescript
// Delete user
DELETE /users/123

Response: 204 No Content
```

## Status Codes

### 2xx Success

- `200 OK` - Request succeeded
- `201 Created` - Resource created
- `204 No Content` - Success, no response body

### 4xx Client Errors

- `400 Bad Request` - Invalid request
- `401 Unauthorized` - Authentication required
- `403 Forbidden` - Authenticated but not authorized
- `404 Not Found` - Resource doesn't exist
- `409 Conflict` - Resource conflict
- `422 Unprocessable Entity` - Validation failed
- `429 Too Many Requests` - Rate limit exceeded

### 5xx Server Errors

- `500 Internal Server Error` - Unexpected error
- `503 Service Unavailable` - Service down

## Response Format

### Standard Response

```json
{
  "data": { ... },
  "meta": {
    "page": 2,
    "limit": 25,
    "total": 100
  }
}
```

### Error Response

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid email format",
    "details": {
      "field": "email",
      "value": "invalid-email"
    }
  }
}
```

## Pagination

### Offset-based

```
GET /users?page=2&limit=25

Response:
{
  "data": [...],
  "meta": {
    "page": 2,
    "limit": 25,
    "total": 100,
    "totalPages": 4
  }
}
```

### Cursor-based (recommended for large datasets)

```
GET /users?limit=25&cursor=abc123

Response:
{
  "data": [...],
  "meta": {
    "limit": 25,
    "nextCursor": "def456"
  }
}
```

## Versioning

### URL Versioning

```
/api/v1/users
/api/v2/users
```

### Header Versioning

```
GET /users
Accept: application/vnd.api.v2+json
```

## Security Best Practices

- Always use **HTTPS**
- Implement **rate limiting**
- Validate **all inputs**
- Use **authentication** (JWT, OAuth)
- Implement **CORS** correctly
- Sanitize **output** to prevent XSS
- Use **CSRF tokens** for state-changing operations
- Implement **CSP headers**
