## 贡献类型

### 接受的变更类型

以下类型的变更最容易被合并：

- **Bug 修复** - 修复已知问题
- **LSP/格式化工具** - 添加新的语言服务器或代码格式化器
- **LLM 性能改进** - 优化 AI 模型交互
- **新提供商支持** - 添加新的 AI 提供商集成
- **环境特定问题修复** - 修复特定平台或环境的问题
- **缺失的标准行为** - 实现缺失的标准功能
- **文档改进** - 改进现有文档

### 需要设计审查的变更

以下类型的变更**必须**在实现前与核心团队进行设计审查：

- **UI 变更** - 任何界面相关的更改
- **核心产品功能** - 新的代理、工具或系统功能

**流程**：

1. 打开 Issue 描述问题和建议的解决方案
2. 等待核心团队审查和批准
3. 获得批准后再开始实现

## 贡献流程

### 1. 选择任务

寻找合适的贡献任务：

- 查看 [Help Wanted](https://github.com/anomalyco/opencode/issues?q=is%3Aissue%20state%3Aopen%20label%3Ahelp-wanted) 标签
- 查看 [Good First Issue](https://github.com/anomalyco/opencode/issues?q=is%3Aissue%20state%3Aopen%20label%3A%22good%20first%20issue%22) 标签
- 查看 [Bug](https://github.com/anomalyco/opencode/issues?q=is%3Aissue%20state%3Aopen%20label%3Abug) 标签
- 查看 [Performance](https://github.com/anomalyco/opencode/issues?q=is%3Aopen%20is%3Aissue%20label%3A%22perf%22) 标签

**提示**：在 Issue 中留言表达您希望处理的意图，维护者可能会将其分配给您。

### 2. 创建 Issue

**Issue-First 策略**：所有 PR 必须引用现有的 Issue。

#### Bug 报告

使用 [Bug 报告模板](../.github/ISSUE_TEMPLATE/bug-report.yml)，包含：

- 问题描述
- 使用的插件
- OpenCode 版本
- 复现步骤
- 截图或会话分享（使用 `/share` 命令）
- 操作系统
- 终端类型

#### 功能请求

使用 [功能请求模板](../.github/ISSUE_TEMPLATE/feature-request.yml)，包含：

- 标题前缀 `[FEATURE]:`
- 确认功能未被建议过
- 功能详细描述和带来的好处

**注意**：UI 或核心产品功能需要等待设计审查批准后再实现。

#### 问题咨询

使用 [问题模板](../.github/ISSUE_TEMPLATE/question.yml) 提出问题。

### 3. 开发实现

详见 [开发环境设置](#开发环境设置) 部分。

### 4. 提交 Pull Request

详见 [Pull Request 最佳实践](#pull-request-最佳实践) 部分。

### 5. 代码审查

等待维护者审查您的 PR。根据反馈进行修改。

### 6. 合并

如果 PR 通过所有检查并获得批准，将被合并到 `dev` 分支。

## 开发环境设置

### 系统要求

- **Bun** 1.3 或更高版本
- **Node.js** 24+（某些工具需要）
- **Git** 最新版本

### 安装依赖

```bash
# 克隆仓库
git clone https://github.com/anomalyco/opencode.git
cd opencode

# 安装依赖
bun install
```

### 运行开发服务器

```bash
# 在 packages/opencode 目录中运行 OpenCode
bun dev

# 在不同目录中运行 OpenCode
bun dev /path/to/your/project

# 在 opencode 仓库本身中运行
bun dev .
```

### 运行 Web 应用

测试 UI 更改：

```bash
bun run --cwd packages/app dev
```

访问 http://localhost:5173（或输出中显示的端口）。

### 运行桌面应用

```bash
# 运行原生桌面应用
bun run --cwd packages/desktop tauri dev

# 仅运行 web 开发服务器
bun run --cwd packages/desktop dev
```

### 构建独立可执行文件

```bash
./packages/opencode/script/build.ts --single

# 运行构建的可执行文件
./packages/opencode/dist/opencode-<platform>/bin/opencode
```

将 `<platform>` 替换为您的平台（例如 `darwin-arm64`、`linux-x64`）。

### 调试设置

#### VSCode 配置

使用示例配置文件：

- [`.vscode/settings.example.json`](../.vscode/settings.example.json)
- [`.vscode/launch.example.json`](../.vscode/launch.example.json)

#### 手动调试

运行 OpenCode 并附加调试器：

```bash
# 通过 inspect 运行
export BUN_OPTIONS=--inspect=ws://localhost:6499/
bun dev

# 或者
bun run --inspect=ws://localhost:6499/ dev

# 单独调试服务器
bun run --inspect=ws://localhost:6499/ ./src/index.ts serve --port 4096

# 然后附加 TUI
opencode attach http://localhost:4096
```

**注意事项**：

- 如果要在 TUI 中触发服务器代码的断点，可能需要运行 `bun dev spawn`
- 使用 `--inspect-wait` 或 `--inspect-brk` 根据工作流程选择

### 测试

```bash
# 从根目录运行类型检查
bun typecheck

# 运行测试（不要从根目录运行）
cd packages/opencode
bun test
```

## 代码审查标准

### 自动化检查

所有 PR 都会通过以下自动化检查：

1. **PR 标准检查**（`.github/workflows/pr-standards.yml`）
   - PR 标题格式是否符合约定式提交规范
   - 是否链接到相关 Issue
   - 自动添加 `needs:title` 或 `needs:issue` 标签（如果不符合）

2. **类型检查**（`.github/workflows/typecheck.yml`）
   - TypeScript 类型检查

3. **测试**（`.github/workflows/test.yml`）
   - 在 Linux 和 Windows 上运行测试
   - Playwright E2E 测试

4. **重复检测**（`.github/workflows/duplicate-prs.yml`）
   - AI 驱动的重复 PR 检测

5. **AI 代码审查**（通过 `/review` 命令触发）
   - 根据样式指南进行审查
   - 仅限维护者触发

### 代码质量标准

#### 功能性

- 代码必须按预期工作
- 没有引入新的 bug
- 通过所有现有测试
- 新功能有测试覆盖

#### 代码风格

遵循 [STYLE_GUIDE.md](../STYLE_GUIDE.md)：

- **单一函数**：保持逻辑在一个函数内，除非有可重用性或组合优势
- **避免解构**：不要不必要的变量解构，使用 `obj.a` 而不是 `const { a } = obj`
- **避免 try/catch**：尽可能使用 `.catch()` 而不是 `try`/`catch`
- **避免 any**：使用精确的类型，避免 `any`
- **单词命名**：尽可能使用简洁的单词命名
- **避免 let**：优先使用 `const`，避免 `let` 语句
- **避免 else**：使用提前返回或 IIFE 避免 `else` 语句
- **使用 Bun API**：合适时使用 Bun 工具，如 `Bun.file()`

#### 性能

- 代码应高效，避免不必要的计算
- 正确处理异步操作
- 适当使用缓存

#### 安全性

- 不引入安全漏洞
- 正确处理用户输入
- 遵循安全最佳实践（参考 [SECURITY.md](../SECURITY.md)）

#### 文档

- 复杂逻辑有注释
- 公共 API 有 JSDoc 注释
- 变更在 PR 描述中解释

### 审查流程

1. **自动化检查通过**
   - 所有 CI/CD 检查必须通过
   - 修复任何类型错误或测试失败

2. **维护者审查**
   - 维护者审查代码和 PR 描述
   - 可能请求更改或提供反馈

3. **迭代改进**
   - 根据反馈进行修改
   - 推送新提交到 PR 分支

4. **批准和合并**
   - 一旦获得批准并通过所有检查，PR 将被合并

## 提交规范

### 约定式提交格式

所有提交消息必须遵循约定式提交格式：

```
<type>(<scope>): <description>
```

#### 类型

- `feat`: 新功能或功能
- `fix`: Bug 修复
- `docs`: 文档或 README 更改
- `chore`: 维护任务、依赖更新等
- `refactor`: 代码重构，不改变行为
- `test`: 添加或更新测试

#### 作用域（可选）

指示受影响的包：

- `app`: app 包
- `desktop`: desktop 包
- `opencode`: opencode 包
- `web`: web 包
- `i18n`: 国际化
- `ui`: UI 组件
- 其他包名

#### 示例

```
feat: add dark mode support
fix(app): resolve crash on startup
docs: update contributing guidelines
chore: bump dependency versions
feat(desktop): add keyboard shortcuts
refactor(opencode): simplify provider API
test: add unit tests for auth module
```

### 提交消息最佳实践

- **简短描述**：使用祈使句，现在时态（"add" 而不是 "added" 或 "adds"）
- **小写**：首字母小写
- **不句号**：描述末尾不加句号
- **详细主体**：如果需要，在描述后空一行添加详细解释

**好的示例**：

```
feat: add support for custom MCP servers

Allow users to connect to custom MCP servers by specifying
the server URL in the configuration. This enables use of
third-party MCP servers beyond the default set.
```

**不好的示例**：

```
Added support for custom MCP servers.
Add Support For Custom MCP Servers.
feat: added custom mcp server support.
```

### 提交频率

- **原子提交**：每个提交应该是一个完整的、可理解的单元
- **频繁提交**：不要长时间工作不提交，频繁提交有助于代码审查
- **清晰的提交历史**：保持提交历史干净，如果需要，使用交互式 rebase 清理

## Pull Request 最佳实践

### PR 前检查清单

在提交 PR 之前，确保：

- [ ] 已阅读并遵循 [CONTRIBUTING.md](../CONTRIBUTING.md)
- [ ] 已阅读并遵循 [STYLE_GUIDE.md](../STYLE_GUIDE.md)
- [ ] 已链接到相关 Issue（使用 `Fixes #123` 或 `Closes #123`）
- [ ] PR 标题遵循约定式提交格式
- [ ] 已通过本地类型检查（`bun typecheck`）
- [ ] 已通过本地测试（如果适用）
- [ ] 代码符合样式指南
- [ ] 复杂逻辑有注释
- [ ] PR 描述清楚说明变更内容和原因

### PR 标题

PR 标题必须遵循约定式提交格式：

- 使用正确的类型前缀（`feat:`、`fix:`、`docs:`、`chore:`、`refactor:`、`test:`）
- 可选地包含作用域（`feat(app):`、`fix(desktop):`）
- 简短描述

**自动化检查**：`.github/workflows/pr-standards.yml` 会检查 PR 标题格式，如果不符合同自动添加 `needs:title` 标签。

### PR 描述

使用 PR 模板：

```markdown
### What does this PR do?

[Brief description of what the PR does]

### How did you verify your code works?

[Explanation of how you verified the changes work]
```

#### 额外建议

- **引用 Issue**：使用 `Fixes #123` 或 `Closes #123` 链接到 Issue
- **解释变更**：简要说明改变了什么以及为什么
- **避免 AI 生成长文**：保持描述简洁明了，不要生成大段 AI 文本
- **添加截图**：UI 变更必须包含截图或视频（修改前和修改后）
- **验证方法**：逻辑变更需要解释如何验证工作

**UI 变更示例**：

```markdown
### What does this PR do?

Add dark mode toggle to the settings panel.

This PR implements a dark mode switch in the settings panel that
persists user preference across sessions.

### How did you verify your code works?

1. Opened settings panel
2. Toggled dark mode switch
3. Verified theme changes immediately
4. Refreshed page to verify persistence
5. Tested in light and dark modes

**Screenshots**:

Before:
[Light mode screenshot]

After:
[Dark mode screenshot]
```

**逻辑变更示例**：

```markdown
### What does this PR do?

Fix memory leak in session cleanup.

When sessions are deleted, the cleanup function wasn't properly
removing event listeners, causing memory to accumulate over time.
This fix ensures all listeners are removed.

**Fixes**: #1234

### How did you verify your code works?

1. Created multiple sessions (10+)
2. Deleted all sessions
3. Used Chrome DevTools Memory profiler
4. Confirmed memory returned to baseline after deletion
5. Verified no event listener warnings in console
```

### PR 大小

- **保持小而专注**：单个 PR 应该解决一个问题
- **避免大 PR**：大 PR 更难审查，更容易引入 bug
- **拆分大任务**：如果 PR 变得太大，考虑拆分为多个小 PR

### PR 更新

- **响应反馈**：及时响应审查者的评论
- **清晰沟通**：如果有问题，请提问
- **迭代改进**：根据反馈进行修改
- **新提交**：推送新提交到 PR 分支，不要修改历史（除非被要求）

### PR 合并后

- **删除分支**：PR 合并后删除您的分支
- **关闭相关 Issue**：如果 PR 引用了 Issue，Issue 会自动关闭
- **关注发布**：您的更改将在下一个版本中发布

## 社区规范

### 尊重和包容

- **尊重他人**：以尊重和专业的态度对待所有社区成员
- **包容性**：欢迎来自不同背景的贡献者
- **建设性反馈**：提供有用的、建设性的反馈
- **接受反馈**：对他人反馈保持开放态度

### 沟通渠道

- **GitHub Issues**：用于 bug 报告、功能请求和讨论
- **Pull Requests**：用于代码审查和讨论
- **Discord**：用于实时讨论和问答（https://opencode.ai/discord）
- **Twitter/X**：关注更新和公告（https://x.com/opencode）

### 问题讨论

- **在 Issue 中讨论**：保持讨论在 GitHub Issue 中，以便所有人可见
- **避免重复**：在提出问题前，搜索现有的 Issue
- **使用标签**：使用适当的标签帮助分类和追踪问题
- **及时更新**：如果您解决了问题，请更新或关闭 Issue

### 行为准则

虽然没有单独的 CODE_OF_CONDUCT.md 文件，但我们期望社区成员：

- 保持专业和尊重
- 避免人身攻击或不适当的语言
- 尊重不同的观点和意见
- 协作解决问题
- 在讨论中保持友好和耐心

### 举报不当行为

如果您遇到或目击不当行为：

1. 通过 GitHub [Security Advisory](https://github.com/anomalyco/opencode/security/advisories) 报告
2. 联系项目维护者（thdxr, adamdotdevin, fwang, jayair, kommander）

## 常见问题

### Q: 我可以提交什么样的 PR？

**A**: 欢迎以下类型的 PR：

- Bug 修复
- LSP/格式化工具
- LLM 性能改进
- 新提供商支持
- 环境特定问题修复
- 缺失的标准行为
- 文档改进

UI 或核心产品功能需要先进行设计审查。

### Q: PR 没有链接 Issue 可以吗？

**A**: 不可以。所有 PR 必须引用现有的 Issue（docs/refactor PR 除外）。这有助于维护者进行分类并防止重复工作。

### Q: 如何找到合适的任务？

**A**: 查看带有以下标签的 Issue：

- `help wanted` - 需要帮助的问题
- `good first issue` - 适合新贡献者的问题
- `bug` - Bug 报告
- `perf` - 性能问题

### Q: 我的 PR 被标记了 `needs:title` 或 `needs:issue` 怎么办？

**A**: 查看自动化机器人添加的评论，它会告诉您具体问题：

- `needs:title`: PR 标题不符合约定式提交格式，需要修改
- `needs:issue`: PR 没有链接到 Issue，需要添加 `Fixes #123` 或 `Closes #123`

### Q: 如何设置开发环境？

**A**: 详见 [开发环境设置](#开发环境设置) 部分。简单步骤：

```bash
bun install
bun dev
```

### Q: 如何运行测试？

**A**:

```bash
# 类型检查
bun typecheck

# 测试（在 packages/opencode 目录中）
cd packages/opencode
bun test
```

### Q: UI 变更需要什么？

**A**: UI 变更必须：

1. 在实现前进行设计审查（UI 或核心功能）
2. 在 PR 中包含截图或视频（修改前和修改后）
3. 清楚说明变更内容

### Q: 如何调试 OpenCode？

**A**: 详见 [开发环境设置](#开发环境设置) 中的调试部分。可以使用：

- VSCode 调试配置
- 手动 inspect 模式
- 分离服务器和 TUI 调试

### Q: PR 多久会被审查？

**A**: 审查时间因维护者可用性而异。一般情况：

- 小 PR：几天内
- 大 PR：可能需要更长时间
- 如果一周内没有审查，可以在 PR 中友好地提醒

### Q: 可以提交 AI 生成的代码吗？

**A**: 可以，但请：

- 确保代码经过您的审查和理解
- 能够解释代码的工作原理
- 不要在 PR 描述中使用 AI 生成的长篇文本
- 保持描述简洁，用您自己的话解释

### Q: 如何成为维护者？

**A**: 维护者是基于持续贡献和信任邀请的。要成为维护者：

- 持续贡献高质量代码
- 积极参与代码审查
- 帮助其他贡献者
- 深入理解项目
- 表现出责任感和判断力

### Q: 发现安全漏洞怎么办？

**A**: 请通过以下方式报告：

1. GitHub [Security Advisory](https://github.com/anomalyco/opencode/security/advisories)
2. 发送邮件到 security@anoma.ly

不要在公开 Issue 中报告安全漏洞。
